# Security policy

Airlock is a local proxy that removes identifying and secret strings from requests before
they reach a cloud LLM or a search provider. What it is designed to stop, what it
guarantees and — at length — what it does **not** protect against are in
[Threat model and limitations](README.md#threat-model-and-limitations) in the README.
Please read that section before relying on Airlock for anything real.

## Status

This is a hackathon project, version 0.1.0. It has not been independently audited. The
measured numbers in the README come from synthetic evaluation data and one attacker model,
and the README says where they are optimistic. Treat it as a prototype.

## Reporting a vulnerability

Use GitHub's private vulnerability reporting:
[**Report a vulnerability**](https://github.com/tristan-kkim/airlock/security/advisories/new).
That keeps the report private until there is a fix. If you would rather use email,
tristan@cortexys.team reaches the same person.

Useful in a report: the version or commit, the configuration (`AIRLOCK_PROTECTION_LEVEL`,
`AIRLOCK_SUBSTITUTION`, detector backend), and an input that reproduces it. Synthetic data
only, please — do not send real personal information or real credentials.

What is interesting:

- A string Airlock had already detected, or one you declared with `/vault/terms`, leaving
  through the proxy in any field. The gate is meant to make this impossible, so it is the
  most serious class of bug.
- An encoding or obfuscation that carries a known string past the gate, beyond the ones the
  README already lists as uncovered (translation, transliteration, hex, ROT13, splitting a
  value across messages, more than two encoding layers).
- Reaching the local API from another origin or another host, past the loopback bind and
  the `Host` header check.
- An unguarded agent run — one that sends raw documents or raw queries — reachable over
  HTTP or the CLI.
- Anything that reads the vault or the audit database through the API.

Detector misses are expected rather than vulnerabilities: the detector is a model plus
rules and it will fail on unusual inputs. Those are welcome as regular issues, ideally with
a case that can join the evaluation set.

## Credentials in this repository

Every API key, JWT, database password and personal detail committed here is fabricated.
They are inputs the detector is measured against: `eval/cases/` and `eval/results/` are
generated by `canary()` in [`eval/generate.py`](eval/generate.py), `scripts/local_model/`
holds hand-written probe cases, and the demo presets and tests use the same kind of fake
values. A secret scanner pointed at this repository **will** report them;
[`.gitguardian.yaml`](.gitguardian.yaml) and
[`.github/secret_scanning.yml`](.github/secret_scanning.yml) list those paths.

No live credential is committed. Local keys live in `.env`, which is gitignored — see
[`.env.example`](.env.example) — and the hosted demo reads its keys from the platform
secret store ([`deploy/nebius/deploy.sh`](deploy/nebius/deploy.sh)). If you believe you
have found a real one, please report it privately using the link above rather than opening
an issue.
