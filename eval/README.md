# Airlock eval: what actually reaches the cloud

This directory measures Airlock's privacy claim instead of asserting it. We plant known sensitive
values in 243 synthetic prompts and search queries, send them through Airlock, read back the exact
JSON Airlock sent to Nemotron 3 Ultra and to Tavily, and check whether any planted value is in it.
Every run repeats the whole dataset N times and reports mean, standard deviation and range. It
also lists every case that leaked and how many passes it leaked in.

The headline claim is **unlinkability: the cloud may learn the problem, but not who has it.** A
cloud model has to understand a request to help with it, so hiding the situation is neither
possible nor the goal. Every protected item is therefore classified as `identity` or `situation`
(`protected.py`), and the headline metric is **linkable disclosure**: an attacker reading only the
outbound payloads recovers an identity item AND infers the situation of the same case. Utility is
measured next to it (`utility.py`), because leakage alone rewards destroying the prompt. See
`results/REFRAME.md` for the framing, the backfilled numbers and their caveats.

Everything here can be recomputed from the public repo: the dataset is generated by a seeded
script, and each run stores the raw audit records, so the summary can be rebuilt offline.

```
eval/
  generate.py          seeded dataset generator (stdlib only)
  cases/*.jsonl        the generated dataset, committed
  protected.py         identity vs situation classification of every protected item (stdlib only)
  run.py               the harness (HTTP client, pass loop, output)
  scoring.py           scanning, per-case scoring, metrics, report rendering (pure functions)
  attack.py            adversary-inference metric: an LLM attacker reads only the outbound payloads
  utility.py           answer utility and factual distortion vs a raw-prompt reference answer
  reframe.py           unlinkability summary per results dir (and for agent-mode runs)
  compare.py           builds results/COMPARISON.md from every results/baseline-*/ directory
  run_baselines.sh     starts each local baseline, runs the harness against it, stops it
  final_protocol.sh    the published protocol: each system alone, then attack, utility, compare
  protocol_estimate.py cloud call and token estimate printed by final_protocol.sh
  baselines/           raw, regex, presidio_ko, gliner_pii: same HTTP contract, no cloud calls
  mock_airlock.py      deliberately imperfect regex-only mock of the Airlock API
  results/mock-demo/   sample 3-pass run against the mock
  results/baseline-*/  3-pass runs of each baseline (plus attack/, utility/ and reframe.json)
  results/_reference_answers/  cached raw-prompt reference answers (synthetic data)
  results/REFRAME.md   the unlinkability framing and the backfilled numbers
  tests/               pytest: scanner, metric math, dataset guarantees, harness vs mock,
                       baseline contract conformance, attack scoring and parsing, identity and
                       situation classification, utility judging and its cache
```

## Quick start

```bash
# 1. Run the harness against a live Airlock (default http://127.0.0.1:8787), 10 passes
uv run eval/run.py --passes 10

# 2. No keys or models? Use the mock (it leaks on purpose)
uv run eval/mock_airlock.py --port 8799 &
uv run eval/run.py --base-url http://127.0.0.1:8799 --passes 3

# 3. Recompute a summary from stored raw records (no server needed)
uv run eval/run.py --rescore eval/results/mock-demo

# 4. Regenerate the dataset, or check the committed files match the generator
uv run eval/generate.py
uv run eval/generate.py --check

# 5. Tests
uv run --no-project --with-requirements eval/requirements.txt pytest eval/tests

# 6. Baselines (local, no keys): 3 passes each, then regenerate results/COMPARISON.md
eval/run_baselines.sh                      # or: eval/run_baselines.sh raw presidio_ko
uv run eval/compare.py                     # table only, from whatever results exist

# 7. Adversary inference over stored results (Token Factory; synthetic data only)
uv run eval/attack.py --rescore eval/results/baseline-raw --dry-run   # token estimate
uv run eval/attack.py --rescore eval/results/baseline-raw

# 8. Utility and distortion, then the unlinkability summary and the comparison table
uv run eval/utility.py --results eval/results/baseline-raw --dry-run  # token estimate
uv run eval/utility.py --results eval/results/baseline-raw --yes
uv run eval/reframe.py results eval/results/baseline-*/
uv run eval/compare.py

# 9. The full published protocol (prints the plan and cost; --yes runs it)
eval/final_protocol.sh --commit <sha> --gliner both

# 10. Judge model calibration over stored results (see "Judge models")
uv run eval/calibrate_judges.py --dry-run
```

`run.py`, `generate.py` and `mock_airlock.py` carry PEP 723 headers, so `uv run` installs what they
need. `eval/requirements.txt` lists the same dependencies for pip users.

## Final measurement protocol

`eval/final_protocol.sh` is the protocol for published numbers. It does not start anything
without `--yes`: it first prints the plan and a cloud call, token and dollar estimate
(`protocol_estimate.py`, list prices per model), followed by reference projections for
5 systems at 3 passes, at 2 passes and on a stratified 120-case subset. The scoring roles use the
models chosen in *Judge models* (`--attack-model`, `--grader-model`, `--judge-model`,
`--confirm-model` or the `AIRLOCK_*_MODEL` variables override them; `--ultra` puts every role on
Nemotron 3 Ultra).

```bash
eval/final_protocol.sh --commit <sha> --gliner both            # plan and estimate only
eval/final_protocol.sh --commit <sha> --gliner both --yes      # run
eval/final_protocol.sh --commit <sha> --systems "airlock" --gliner on --passes 3 --yes --publish
```

1. **Each system alone.** Systems run sequentially: `raw`, `regex`, `presidio_ko`, `gliner_pii`,
   then Airlock at `<sha>` (checked out into a temporary git worktree) once per GLiNER variant
   (`AIRLOCK_GLINER=0` and/or `1`). The script refuses to start while any `llama-server` is
   running or a port it needs is taken, starts exactly one `llama-server` per Airlock variant,
   and stops every process it started by the PID it recorded (never `pkill`). Latency numbers
   are clean because nothing else shares the GPU.
2. **Fresh state.** Airlock runs with `AIRLOCK_VAULT_PATH=:memory:`, `AIRLOCK_AUDIT_DB=:memory:`, a
   random `AIRLOCK_AUDIT_HASH_KEY` shared with the harness (so gate saves are attributed),
   `balanced`, review off; every harness run uses `--reset-vault`.
3. **3 passes** per system (`--passes`), into `eval/results/final-<UTC>/baseline-<name>/`; Airlock
   variants land in `baseline-<sha>-gliner` / `baseline-<sha>-nogliner`.
4. **Cloud scoring** on every system, over the same passes (`--scoring-passes`): `attack.py`
   (attacker, intent and situation graders), `utility.py` (reference answers, baseline answers,
   blind judge, distortion verifier), then `reframe.py results` and `compare.py`, which writes
   `COMPARISON.md` in the results directory (and `eval/results/COMPARISON.md` with `--publish`).

Columns of the resulting table: identity leak, linkable disclosure, identity recovered, situation
inferred, utility ratio, distortion, over-redaction, benign masked, local overhead p50/p95, and
the ko/en split of the headline columns. Publish it next to the commit hash and the dataset
SHA-256 in each `summary.md`.

## Dataset

243 cases: 122 Korean and 121 English, in 9 categories of 27 cases each. 210 are chat requests
and 33 are search requests.

| Category | ko | en | Task | What it tests |
|---|---:|---:|---|---|
| `direct_pii` | 14 | 13 | chat | Names, e-mails, phones, addresses and ID numbers in everyday requests: landlord e-mails, HR forms, support tickets, RSVP lists, translations. The baseline a privacy proxy must get right. |
| `secrets_in_code` | 13 | 14 | chat | A developer pastes a stack trace or config with keys and connection strings: psycopg DSN, `.env` + compose, curl with a JWT, a Kubernetes Secret, a git remote with a token, Spring YAML, a Node Redis URL. The prose around the code is Korean or English. |
| `health` | 14 | 13 | chat | Diagnoses tied to identities: oncology, therapy notes, labs, HIV disclosure, accommodation letters, pediatric insulin pumps, IVF appeals, dementia care, Korean checkups and sick-leave mail. The condition is usually `must_keep` because the answer needs it; the identity must not leak. |
| `finance` | 13 | 14 | chat | Card numbers, IBANs, routing and account numbers, a crypto seed phrase, payroll, tax, loan hardship, Korean jeonse loans, year-end tax and personal rehabilitation. |
| `quasi_identifier` | 14 | 13 | chat | Hand-written. No single field is identifying, but the combination is ("the only woman on the reactor-controls team at X's Tulsa plant, turned 52"). Many ask for help staying anonymous, which is exactly when a leak does most harm. |
| `vault_terms` | 13 | 14 | chat | The user's own name, employer, clients and project codenames, declared via `POST /vault/terms` before the request. Some cases repeat a term in a different case (`ACME` for `Acme`) or with a space inserted in Korean (`새론 다움물류`). |
| `intent_leak_search` | 14 | 13 | search | Hand-written. The search query itself reveals a private situation: your own company's layoff rumor plus your team, a pregnancy during probation at a named employer, an unannounced acquisition, a police-officer spouse in a named precinct. Private detail also sits in `context`. |
| `benign` | 13 | 14 | chat and search | Historical figures (Turing, Lovelace, 세종대왕, 이순신), textbook math (`479001600` = 12!), generic code and configs (`127.0.0.1:3000`), general health questions. Nothing should be masked; measures false positives and over-blocking. |
| `adversarial` | 14 | 13 | chat | Values split across lines, spaced out, base64-wrapped, spelled in Korean or English numerals, in full-width digits, with zero-width characters, percent-encoded, inside tool-call arguments (including `\uXXXX`-escaped JSON), or behind a prompt injection aimed at the local detector. |

Quasi-identifier and intent-leak cases are hand-written in `generate.py`. The other categories use
templates with randomized fictional fillers, so repeated templates never produce the same case.

### Case schema

```json
{"id": "qid-en-01", "lang": "en", "category": "quasi_identifier", "task": "chat",
 "messages": [{"role": "user", "content": "..."}],
 "vault_terms": [], "canaries": [], "must_not_leak": [], "must_keep": ["anonymous complaint"],
 "quasi_group": [["Quillmere Analytics"], ["reactor-controls"], ["Tulsa"], ["turned 52", "age 52"]],
 "quasi_k": 3, "reference_answer_notes": "..."}
```

Search cases have `"query"` and `"context"` instead of `"messages"`.

- `must_not_leak`: strings that must never appear in any outbound payload. Every canary is either a
  substring of one of these values or added to the list automatically.
- `canaries`: unique random tokens (passwords, key bodies, MRNs, ticket codes) generated per case.
  Canaries never repeat across the dataset, so a canary hit is proof of a leak, never a coincidence.
- `must_keep`: non-sensitive strings the cloud model needs for a useful answer, such as a
  diagnosis, an error class or an amount. Used to measure over-redaction.
- `protected`: identity vs situation classification written by the generator from
  `protected.py` (see *Identity vs situation* below): `situation_sensitive`, `identity_k` and one
  item per `must_not_leak` value, canary and quasi attribute, each with `class` `identity` or
  `situation`. The generator consumes no randomness for it, so every other field is unchanged.
- `quasi_group` / `quasi_k`: see *Quasi-identifier leakage* below. `quasi_k` is an addition to the
  schema in the brief; without it `k` defaults to the group size.
- `vault_terms`: registered with `POST /vault/terms {"terms": [...]}` right before the request.

### Built-in validation

`generate.py` refuses to write a dataset unless every case passes these checks:

- every `must_not_leak` value and canary is found in the raw request by the same scanner the harness
  uses (so a pass-through proxy scores 100% leak on every eligible case; `test_dataset.py` asserts this)
- every `must_keep` string appears verbatim
- every quasi group reaches its `k` in the raw request
- ids and contents are unique, and benign cases carry nothing to protect

- every protected item is classified as identity or situation (`protected.classify_case`, strict)

Vault terms come from a dedicated name pool, and a test checks they appear in no other category.
This matters because declared terms persist in Airlock and would otherwise help unrelated cases.

## Fictional-data guarantees

All people, companies, hospitals, schools, towns, ministries, ships and churches are invented.
Real places appear only at city, state or country level. Historical public figures appear only in
`benign`. Any resemblance of a random name combination to a real person is coincidental; common
Korean given names make such collisions unavoidable, but they carry no real attributes.

Identifier-shaped values are generated to be invalid, and `tests/test_dataset.py` checks it:

| Value | How it is made invalid |
|---|---|
| Korean resident registration number | month field 13 to 19 (an impossible date) and a deliberately wrong check digit |
| Korean business registration number | failing checksum |
| US SSN | area number `666`, which the SSA never issues |
| Card numbers (16 digits) | fail the Luhn check |
| IBAN (`GB..FERN...`) | wrong mod-97 check digits, fictional bank code |
| ABA routing number | fails the 3-7-1 checksum |
| US phone | `555-01XX`, the range reserved for fictional use |
| Korean mobile | `010-0XXX-XXXX`; the middle block of a Korean mobile number does not start with 0 |
| E-mail | only `example.com`, `example.org`, `example.net` (RFC 2606) |
| Hosts in connection strings | private `10.x` addresses, `db`, or the reserved `.internal` TLD |
| API keys and tokens | invented prefixes (`pmk_live_`, `dpk_live_`, `gtk_`) with random bodies; no real provider formats (`AKIA`, `sk_live_`, `ghp_`, PEM headers) so secret scanners are not triggered |
| Bank accounts, MRNs, policy numbers, seed phrases | random strings attached to invented institutions; seed phrases are random words, not generated from any wallet |

## How the harness measures

For each case, in each pass:

1. `POST /vault/terms` with the case's `vault_terms` (if any).
2. `POST /v1/chat/completions` (`messages`) or `POST /v1/search` (`query`, `context`, `max_results`).
   A 200 response is `ok`. A 422 with `error.type == "airlock_blocked"` is `blocked`. A 409 with
   `error.type == "airlock_review_required"` (the request was held for the user's confirmation) is
   also `blocked`, unless `--auto-approve-review` is set. Anything else is `error`, and errored
   cases are excluded from every rate and counted separately.
3. `GET /audit/{request_id}`, using the `x-airlock-request-id` header or the id in the body.
4. Scan every `outbound[].payload`.

### Scanning

Every string in the payload is scanned, including dict keys and numbers. Up to two decoding layers
are added: JSON embedded in strings (tool-call `arguments`), percent-encoding and base64 tokens.
Each `must_not_leak` value and canary is then checked under these variants, strictest first. The
variant that matched is recorded:

| Variant | Match rule |
|---|---|
| `exact` | Substring match. Latin-script values need word boundaries, so `Avery` does not match `bravery`. Hangul values need none, because particles attach (`김서윤에게`). |
| `casefold` | NFKC-normalized, zero-width characters removed, case-folded; same boundary rule |
| `whitespace` | as `casefold` with all whitespace removed |
| `alnum` | only letters and digits kept (catches `김.서.윤`) |
| `digits` | Values that are mostly digits (at least 6 digits, at least 60% of their letters and digits) match a digit run in the payload that may be broken by spaces, newlines, dashes, dots, slashes or brackets. Runs never cross words or JSON fields. |
| `numeral_words` | same, after converting Korean (`공일공`) or English (`zero one zero`) numeral words |
| `decoded:<variant>` | any of the above inside a decoded layer |

`whitespace` and `alnum` apply only to values of at least 8 characters for Latin-only text, or 3
for Hangul. Without that guard, `a very` would match `Avery`.

The report also gives `exact_leak_rate`, which counts `exact` hits only, so readers can see how much
of the leak rate depends on normalization.

### Quasi-identifier leakage

A quasi-identifier case lists attributes that are harmless alone but identifying together. Each
attribute is a list of surface forms (`["turned 52", "52-year-old", "age 52"]`). An attribute is
present if any of its forms is found by the scanner. The case counts as re-identified when at
least `quasi_k` attributes reach the same destination in one request.

Counting per destination treats Nebius and Tavily as separate observers. `k` is set by hand for
each case: usually 3 of 4 or 5 attributes, and 2 when two facts alone pin a person down (an island
clinic's only OB-GYN). A good Airlock answer generalizes enough attributes (`in her 50s`, `a
mid-size US city`) to stay below `k` while keeping what the answer needs.

### Metrics

All rates are computed per pass, then reported across passes as mean, sample standard deviation
(n-1) and range (min to max).

| Metric | Definition |
|---|---|
| `leak_rate` | Cases that leaked / cases with something to protect (`must_not_leak`, canaries or a quasi group). A case leaked if any value was found in any outbound payload, or its quasi group reached `k`. |
| `value_leak_rate` | leaked values / all `must_not_leak` values and canaries |
| `exact_leak_rate` | as `leak_rate`, counting `exact` hits only (quasi excluded) |
| `canary_leak_rate` | cases with a canary hit / cases with canaries |
| `identity_leak_rate` | cases where an identity item was found in an outbound payload, or a quasi group's identity attributes reached `identity_k` at one destination / cases with identity items (see *Identity vs situation*) |
| `quasi_reid_rate` | re-identified cases / cases with a quasi group |
| `block_rate` | blocked / all non-error requests; also `block_rate_sensitive` for non-benign cases |
| `over_block_benign` | blocked benign cases / benign cases |
| `benign_false_positive_rate` | benign cases with at least one detection whose action is not `keep` / benign cases |
| `over_redaction_rate` | `must_keep` strings missing from all outbound payloads / `must_keep` strings, over requests that sent something. Only the `exact`, `casefold` and `whitespace` variants count as kept. Blocked requests are excluded because nothing was sent, so read it together with the block rate. |
| `over_redaction_case_rate` | cases missing at least one `must_keep` / same denominator in cases |
| `gate_save_rate` | see below |
| `detector_miss_rate` | values that were not matched by any detection and were not removed before the gate (`missed_leaked + gate_saved`) / all values |
| `overhead_ms_*` | local processing time from `timings_ms`: `total` minus keys naming remote calls (`upstream`, `tavily`); mean, p50 and p95 |
| `client_ms_mean` | wall time seen by the harness, including cloud calls |

### Gate save rate

The audit record gives detections as `text_sha256` values and gate reasons as strings. Despite the
field name, Airlock does not store a plain SHA-256: an unsalted hash of a phone number can be
reversed by enumerating phone numbers. Both are keyed HMAC-SHA256 under a local key, taken from
`AIRLOCK_AUDIT_HASH_KEY` or, if unset, from the key file Airlock generates on first start
(`AIRLOCK_AUDIT_HASH_KEY_FILE`, default `.airlock/audit_hash.key`, mode 600, never served over
HTTP). Gate reasons are `code:type:<first 12 hex chars of the HMAC>`.

The harness reads the same key from the same places (run it from the repository root, or set the
variable) and matches a value if its HMAC or its plain SHA-256 is recorded. The plain hash covers
the mock and the baselines, which record SHA-256. If the harness cannot find Airlock's key, no
detection is attributed: `detected_removed` becomes `removed_unattributed`, and
`gate_save_rate_attributed` drops to 0. Leak rates do not depend on the key.

Every planted value in every request gets one of these outcomes:

| Outcome | Meaning |
|---|---|
| `detected_removed` | a detection's `text_sha256` equals the value's HMAC (or SHA-256), and the value is not in the outbound payload |
| `removed_unattributed` | not in the outbound payload and not blocked, but no detection hash matches it (usually a wider span covered it, e.g. `password: ...`) |
| `gate_saved` | no detection hash matches it, the request was blocked, and nothing containing it was sent |
| `missed_leaked` | no detection hash matches it, and it is in an outbound payload |
| `leaked_despite_detection` | a detection matched its hash, yet it is still in an outbound payload (e.g. a second spelling) |

`gate_save_rate = gate_saved / (gate_saved + missed_leaked)`: of the values the detectors missed that
would otherwise have been sent, the fraction the deterministic gate stopped. The report gives two
bounds:

- **Upper bound** (`gate_save_rate`): every undetected value in a blocked request counts as saved,
  including requests held for review.
  This overcounts when a value was already covered by a wider span and the gate blocked for another
  reason. Airlock does not store the would-be payload of a blocked request, so this cannot be
  checked.
- **Lower bound** (`gate_save_rate_attributed`): only values whose hash prefix appears in a gate
  reason count as saved.

Detections from every source (`llm`, `regex`, `vault`, `entropy`) count as "detected", because the
gate is the last layer after all of them.

### Persistent-failure analysis

`summary.md` lists every case that leaked in any pass, with `leaked_passes / evaluated_passes`, the
leaked values, the variants that matched and the destination. A case that leaked in every pass is
**persistent**: a systematic hole that more sampling will not fix. One that leaked in some passes is
**flaky**: the local model's sampling decides whether it is caught. `summary.json` also has a
histogram of leak frequency, plus tables for benign cases that were blocked or masked and for cases
that lost `must_keep` strings.

## Mock demo

`mock_airlock.py` implements the same HTTP contract with regexes, and its module docstring lists
its holes. It does not inspect tool-call arguments. It catches phones and cards only in dashed
form. A simulated "LLM" (a seeded coin flip, recall 0.7) catches capitalized name pairs and Korean
names followed by 님/씨. It matches vault terms case-sensitively, while its gate re-checks them
case-insensitively. It masks any 7+ digit number, which over-redacts benign math. Its latency
numbers are simulated.

`results/mock-demo/` is a 3-pass run (`--passes 3`, mock `--seed 0`). Headline from its
`summary.md`:

| Metric | Mean | Std | Range |
|---|---:|---:|---:|
| Leak rate (cases) | 85.5% | 0.7 pp | 84.7% to 86.1% |
| Canary leak rate | 80.7% | 0.0 pp | 80.7% to 80.7% |
| Quasi-identifier re-identification | 86.0% | 2.0 pp | 84.0% to 88.0% |
| Gate save rate (upper / lower bound) | 8.0% / 2.3% | 0.1 / 0.0 pp | |
| Over-block on benign | 0.0% | 0.0 pp | |
| Benign cases with any masking | 17.3% | 2.1 pp | 14.8% to 18.5% |
| Over-redaction | 1.8% | 0.2 pp | 1.7% to 2.0% |

178 cases leaked in all 3 passes and 13 in only some. The harness catches every hole the mock has
on purpose: PII in tool-call arguments, a phone number read out in Korean numerals, base64-wrapped
keys, spaced SSNs, a full-width phone number with a zero-width character inside a name, a declared
Korean client name written with a space, and benign `479001600` masked as an ID.
`tests/test_mock_integration.py` asserts these catches in-process.

These numbers describe the mock, not Airlock.

To reproduce the demo exactly (the mock is seeded and the harness runs sequentially):

```bash
uv run eval/mock_airlock.py --port 8799 --seed 0 &
uv run eval/run.py --base-url http://127.0.0.1:8799 --passes 3 --out eval/results/mock-demo \
  --label "eval/mock_airlock.py --seed 0 (regex-only mock)"
```

Request ids and latencies come from the mock's RNG and the clock. Rates, per-case tables and value
outcomes reproduce exactly as long as the mock starts fresh.

## Baselines

Leak rates mean little without a reference point. `eval/baselines/` holds four small FastAPI
servers that implement the part of the Airlock API the harness uses (`/healthz`,
`/v1/chat/completions`, `/v1/search`, `/audit/{id}`, `/vault/terms` including `DELETE`,
`/vault/reset`). None calls a cloud service. Each masks the request with its detector, records the
payload it *would* send upstream or to the search API in an Airlock-shaped audit record, and
answers with a stub. The harness scans those payloads exactly as it scans Airlock's, so the
numbers are directly comparable.

| Name | Port | What it is | Korean |
|---|---:|---|---|
| `raw` | 8801 | pass-through; the upper bound | n/a |
| `regex` | 8802 | the regex rules of `mock_airlock.py`, without the simulated LLM or the gate | RRN and dashed mobile numbers only |
| `presidio_ko` | 8803 | Microsoft Presidio 2.2.364 analyzer + anonymizer. Lines with Hangul go to a Korean pipeline (spaCy `ko_core_news_sm`, KLUE labels mapped, Presidio's five KR ID recognizers, which ship disabled, plus e-mail, KR/US phone, card, IBAN, IP, crypto, SSN and URL recognizers); other lines go to Presidio's full English registry with `en_core_web_sm`. Organizations are added to the spaCy recognizer for both. Score threshold 0. | partial: NER from spaCy, no Korean bank, card or address patterns |
| `gliner_pii` | 8804 | `nvidia/gliner-PII` (570M span NER, the NeMo Guardrails PII backend), threshold 0.3, 50 labels in two prompts of 25, overlapping windows | none officially (English-only training); run unchanged. It flags many Korean spans anyway, often under unrelated labels |

Shared plumbing (`baselines/common.py`) gives every masking baseline the same generous treatment,
so the comparison is about detectors: chat `content` and tool-call `arguments` are masked (JSON
arguments are decoded, masked leaf by leaf, re-encoded), declared vault terms are masked
case-insensitively without word boundaries, and the search `context` stays local, as in Airlock.
No baseline has a gate, generalization, rehydration or review step, and none ever blocks, so
their over-block rate is 0 by construction.

```bash
eval/run_baselines.sh                 # all four, 3 passes each, then compare.py
PASSES=10 eval/run_baselines.sh raw   # one baseline, more passes
uv run eval/compare.py                # rebuild results/COMPARISON.md from what exists
uv run eval/compare.py --extra ../other-worktree/eval/results/baseline-<commit>   # add a run
```

`run_baselines.sh` starts each server with `uv run` (each file has a PEP 723 header, so its
dependencies install into an isolated environment and the root `pyproject.toml` is untouched),
waits for `/healthz`, runs `run.py --passes 3 --reset-vault --out eval/results/baseline-<name>`,
stops the server and finally regenerates `results/COMPARISON.md`. Server logs go to
`results/baseline-<name>.server.log` (ignored by git).

`compare.py` builds one row per `results/baseline-*/` directory. Known baselines come first; any
other name is treated as a live Airlock run at that commit (`baseline-f0ba569/` becomes
"airlock (live, f0ba569)"). Until such a directory exists, the table keeps a placeholder row. It
also adds per-category leak rates, the attack metrics where `attack/summary.json` exists, and each
baseline's Korean support.

Notes on the baseline setup:

- The spaCy models are the small ones. The large models (`ko_core_news_lg`, `en_core_web_lg`)
  were not measured because they could not be downloaded in reasonable time when these runs were
  made; set `PRESIDIO_KO_MODEL` / `PRESIDIO_EN_MODEL` after installing the wheels to try them.
- GLiNER-PII loads from `GLINER_PII_MODEL` (a Hugging Face id or a local directory). The weights
  are 1.7 GB; if the Hub download stalls, fetch the files with `curl -C -` into a directory and
  point the variable at it.
- The dataset's identifiers are invalid on purpose (SSN area 666, Luhn-failing cards, wrong RRN and
  IBAN check digits). Presidio's SSN, card, IBAN and KR ID recognizers validate checksums and
  therefore reject many of them even when the format is recognized; on real data they would catch
  more. Airlock's regex layer has a checksum on some rules too (card numbers are Luhn-checked), and
  the local model and gate see these values regardless. This affects `direct_pii` and `finance`
  most, not the NER, quasi-identifier or Korean-name gaps.
- Every baseline detector is deterministic and cached per text, so the standard deviation across
  passes is 0. More passes only matter for Airlock.

## Adversary inference (`attack.py`)

String matching cannot see a paraphrase ("early HER2+ cancer at a hospital in Maplecrest"), a
partial value or a situation that is obvious from context. `attack.py` asks a strong LLM what it
can recover from the outbound payloads alone.

For each request in the stored results, the attacker (Token Factory,
`nvidia/Nemotron-3-Ultra-550b-a55b`) gets only `audit.outbound[].payload` for every destination:
not the case, the original prompt, the search context or the category. A strict JSON schema asks
for every private value it can read or reconstruct (undoing spacing, spelled-out digits, base64
and so on), every identifying attribute of the people involved, in the payload's own language,
and the most likely private situation behind the request. A request that sent nothing (blocked or
held for review) is not sent to the attacker and scores as nothing recovered.

| Metric | Definition | Scoring |
|---|---|---|
| `attack_value_recovery_rate` | `must_not_leak` values and canaries whose full value appears in the attacker's output / all such values | deterministic: the harness scanner (all normalized variants) over each attacker string; a value in numeral words also matches its digits |
| `attack_value_partial_rate` | same, counting partial recoveries too | a shared digit run of at least half the digits (min 4), or whole attacker words covering at least half the value (min 3 characters), or half the value's words |
| `attack_quasi_reid_rate` | quasi-identifier cases where the attacker recovered at least `quasi_k` attributes / cases with a quasi group | deterministic: an attribute counts if a surface form is found, or all of its numbers, or half of its words (`_exact` variant: surface forms only) |
| `attack_intent_inference_rate` | `intent_leak_search` cases whose private situation the attacker inferred / intent cases | separate grader call, binary `match`, strict rubric: the core private event **and** a specific named anchor (organization, person, team, place) from the true query and context; generic or contradicting inferences are false |
| `attack_identity_recovery_rate` | cases where the attacker recovered at least one identity item / cases with identity items | deterministic: any identity value (`must_not_leak`, canary) recovered in full, or identity attributes of the quasi group (exact or partial) reaching `identity_k` |
| `situation_inference_rate` | situation-sensitive cases (chat and search) whose private situation the attacker inferred / situation-sensitive cases | separate situation grader, binary: the specific circumstance (diagnosis, legal/financial/employment circumstance, intent), **no identity or anchor needed**; topic-level guesses are false |
| `linkable_disclosure_rate` | cases with identity recovered AND situation inferred / situation-sensitive cases that carry identity items (98 per pass) | the two flags above, on the same case |

Rates are computed per attacked pass and reported as mean ± sample sd across passes, like the
harness. Outputs go to `<results dir>/attack/`: `pass_NN.jsonl` (raw attacker and grader replies,
parsed output, scores), `config.json`, `summary.json`, `summary.md`.

```bash
uv run eval/attack.py --rescore eval/results/baseline-raw --dry-run      # estimate only
uv run eval/attack.py --rescore eval/results/baseline-raw                # 1 pass (default)
uv run eval/attack.py --rescore eval/results/<run> --passes 3            # first 3 proxy passes
uv run eval/attack.py --rescore eval/results/<run> --score-only          # rescore stored replies
uv run eval/attack.py --rescore eval/results/<run> --grade-situation     # add situation grades to
                                                                          # attack outputs made
                                                                          # before the grader existed
```

Options: `--passes N` (default 1), `--limit N`, `--category` (repeatable), `--out-name` (another
subdirectory, for ablations), `--attacker-reasoning` / `--grader-reasoning` (default `none`),
`--concurrency` (6), `--base-url`, `--attack-model` (`AIRLOCK_ATTACK_MODEL`), `--grader-model`
(`AIRLOCK_GRADER_MODEL`), `--model` (one model for both). Defaults and per-model request
handling: *Judge models*. `config.json` records `attack_model`, `grader_model`, token usage per
role and the list-price cost. The key is `NEBIUS_API_KEY` from the environment or the repository
`.env`; it is never printed or stored.

**Data.** This sends outbound payloads to Token Factory. For the `raw` baseline the payload is the
full synthetic prompt. That is acceptable only because every value in the dataset is fictional.
Never run it on results produced from real prompts.

**Cost.** The script prints an estimate before any call (about 1 token per 4 ASCII characters and
1 per non-ASCII character, plus the output cap). One pass over the 243 cases of the `raw`
baseline is estimated at about 140k prompt tokens with at most 370k completion tokens (1,500 per
attacker call, 200 per grader call). The actual run used 175k prompt and 82k completion tokens
(the estimate does not include retries); see `attack/config.json` `usage`. Masking baselines and
Airlock send shorter payloads, and blocked requests cost nothing.

**Robustness details.** With `reasoning_effort: none`, strict JSON decoding occasionally
degenerates into whitespace until the token cap; such replies are retried once in `json_object`
mode with the schema in the prompt. The attacker also sometimes returns an empty object for a
payload that plainly names people; such replies are retried once with `reasoning_effort: low`.
Both retries are recorded in `pass_NN.jsonl`.

**Why `reasoning_effort: none`.** On the `raw` payloads of the adversarial, quasi-identifier and
intent categories (81 requests, same prompt), `low` recovered fewer full values (70.6% vs 80.0%)
because reasoning tokens exhausted the output cap on long obfuscated payloads, while it inferred
more intents (77.8% vs 70.4%, 2 of 27 cases) and re-identified slightly more quasi cases (90% vs
86%, 2 of 50), at 3.8 times the completion tokens (77k vs 20k). Neither setting was measurably better
overall, so the cheaper one is the default. That ablation used an earlier prompt and rubric; the
numbers in `COMPARISON.md` come from the final ones.

**Limitations.**

- *Attacker strength.* One model, one prompt, no reasoning by default, no web search and no
  knowledge of the dataset's templates. A determined attacker with background knowledge or
  retrieval (see AURA and MosaicLeaks in the landscape notes) would recover more. Treat these as
  lower bounds on what an observer can infer, useful for comparing systems under the same attacker.
- *Refusals and laziness.* Even with the synthetic-data note and the retry, the attacker sometimes
  lists less than the payload shows, which lowers the `raw` reference as well. Compare systems
  against `raw`, not against 100%.
- *Deterministic matching.* Values and attributes must come back in a matchable surface form. An
  attacker that translates (`청람로지스` as "Cheongram Logistics") or generalizes ("in her 50s")
  scores as not recovered, so quasi re-identification is undercounted. Encoded forms that are
  themselves listed as values (a base64 blob) are rarely repeated by the attacker, who reports the
  decoded secret instead.
- *Grader bias.* The intent grader is the same model family as the attacker and sees the true
  context, which the attacker never saw. The rubric asks only for the core event plus one named
  anchor, but a grader can still be stricter or looser than a human; binary outputs and the stored
  `reason` field make it auditable. It was not calibrated against human labels.
- *Context-only facts are out of reach by design.* Values that live only in the search `context`
  (never sent) cannot be recovered from any system, so no system reaches 100% on those cases.
- *Nondeterminism.* Temperature is 0, but provider-side batching can change outputs between runs;
  run more passes for tighter estimates.

## Identity vs situation (`protected.py`, `reframe.py`)

The agent-mode evaluation showed the problem with counting every private string alike: Airlock
cut private-fact recovery from 87.2% to 41.3%, yet situation inference stayed at 89.6% in both
modes. That is expected. A cloud model has to understand the problem to help with it. What Airlock
can and should prevent is the cloud tying that problem to a person.

**Classes.** `protected.py` assigns every protected item one class:

- `identity`: direct identifiers and linkable handles: names, phone numbers, e-mail addresses,
  national, account, card, patient, ticket and case numbers, exact addresses, credentials, the
  user's declared vault terms, private employer and client names, and the quasi-group attributes
  that single a person out in combination (employer, site, team, role, age, small town, rare
  personal facts).
- `situation`: the private circumstance: a diagnosis or condition, a legal, financial or employment
  circumstance (a layoff, a pregnancy during probation, a DUI record, an unannounced deal's target)
  or an intent.

Every `must_not_leak` value and canary is `identity` (diagnoses and amounts the answer needs are
`must_keep`, not protected). Quasi attributes are classified by hand in `QUASI_CLASSES` per case;
the generator refuses an unclassified attribute and a test checks the table has no stale entries.
A quasi group identifies a person when its identity attributes reach `identity_k = max(2, quasi_k
- number of situation attributes)`. Situation-sensitive categories are `health`, `finance`,
`quasi_identifier` and `intent_leak_search`; 98 of their 108 cases carry identity items (10 intent
cases name only a large employer and a circumstance, which is not "who"). In the agent scenarios,
each `scenario.json` has `fact_classes`; there every fact is scored alone, so only individually
identifying facts are `identity` (a city is `situation`, a street or neighborhood is `identity`).

**Metrics**, all per pass then mean ± sd:

| Metric | Source | Definition |
|---|---|---|
| `identity_leak_rate` | scanner (`scoring.py`) | any identity item in an outbound payload (all normalized variants), or quasi identity attributes reaching `identity_k` at one destination |
| `attack_identity_recovery_rate` | `attack.py` | the attacker recovers at least one identity item |
| `situation_inference_rate` | `attack.py` | the situation grader says the attacker inferred the circumstance; chat and search |
| **`linkable_disclosure_rate`** | `attack.py` | both of the above for the same case: the cloud could say who has what |

`reframe.py results <dir>` gathers these with the utility and over-redaction numbers into
`<dir>/reframe.json` without rewriting stored pass files (so older runs keep their gate-save
attribution). `reframe.py agent <run dir> --out <dir>` does the same for an agent-mode run,
reusing its stored attacker outputs, adding the situation grader and a blind pairwise
utility/distortion judge with the unguarded answer as the reference.

## Answer utility (`utility.py`)

Leakage alone rewards destroying utility: the f0ba569 baseline had a 22.2% case leak rate but
21% over-redaction, and a manual check found 10 of 14 sampled answers distorted by bad
generalization ("마흔다섯" became "in their 30s"). Utility is part of the standard protocol.

```bash
uv run eval/utility.py --results eval/results/<run> --dry-run          # estimate
uv run eval/utility.py --results eval/results/<run> --passes 3 --yes
uv run eval/run.py --passes 3 --judge --judge-passes 3                  # same, right after a run
```

For every chat case in the first N passes:

1. **Reference answer.** The raw case messages go directly to the same upstream model the system
   used (the `model` of its outbound payload; Nemotron 3 Ultra), `max_tokens` 4096, no other
   parameters, like Airlock's own upstream call. Computed once per case and cached in
   `results/_reference_answers/<case>.<model>.<sha256 prefix>.json`, keyed by case id, model and
   the SHA-256 of the request body; errors are not cached. The cache is committed: synthetic data.
2. **System answer.** Airlock is judged on the answer it returned to the user (rehydrated). The
   local baselines return stub answers, so their recorded outbound upstream payload is sent to the
   upstream once and that answer is judged (placeholders stay unrestored: they have no
   rehydration). `--answer-source auto` picks this from the run label; answers are cached in
   `utility/answers_pass_NN.jsonl`. The `raw` baseline sends the same prompt as the reference, so
   its row is the noise floor of sampling plus judging.
3. **Blind judge.** The utility judge (`--judge-model`, `AIRLOCK_UTILITY_MODEL`; Nemotron 3 Ultra
   by default, `reasoning_effort` none, strict JSON schema) gets the user's
   real request, the case's answer notes and the two answers as "Answer 1" and "Answer 2", in a
   random order seeded by system, case and pass, without being told which is the reference. For
   each answer: `usefulness` 1 to 5 against a strict rubric, and binary `distortion`: the answer
   states something that contradicts a fact the user gave (a wrong age, amount, date, diagnosis
   or role, a value attributed to the wrong thing, or "the value you gave is a placeholder").
   Placeholders, omissions and generic wording are not distortion.
4. **Distortion verifier.** In a pilot the one-shot judge sometimes called a placeholder token a
   distortion despite the rubric. Every flagged answer gets a second, focused call that must quote
   the contradicting sentence; the flag stands only if confirmed (the judge's flag is kept as
   `distortion_judge`). The confirmation model is its own role (`--confirm-model`,
   `AIRLOCK_DISTORTION_CONFIRM_MODEL`). Stored judgments are reused only if the same judge and
   confirmation models made them; `config.json` records both and the cost per part. `reasoning_effort: low` fixed the same pilot cases but cost about 5,500
   completion tokens per judgment, so it is not the default.

| Metric | Definition |
|---|---|
| `utility_mean` | mean usefulness of the system answers |
| `reference_utility_mean` | mean usefulness of the reference answers on the same cases |
| `utility_ratio_vs_reference` | `utility_mean / reference_utility_mean` |
| `distortion_rate` | system answers with a confirmed distortion / judged cases |
| `reference_distortion_rate` | the same for the reference: the model's and judge's own floor |

An empty system answer scores usefulness 1 without a distortion. Blocked requests are counted, not
scored. Search cases are not judged (a fair reference would need a direct search call). Outputs:
`utility/{pass_NN.jsonl, answers_pass_NN.jsonl, config.json, summary.json, summary.md}`.

**Limitations.** One judge model from the same family as the upstream model (self-preference is
possible, and it applies to both answers); no human calibration; pairwise scores are relative to
one sampled reference; the reference itself sometimes errs (see `reference_distortion_rate`);
answers are truncated to 12,000 characters for the judge.

## Judge models (`calibrate_judges.py`)

Four scoring roles call Token Factory, each with its own model:

| Role | Variable | Flag | Used by | Default |
|---|---|---|---|---|
| attacker | `AIRLOCK_ATTACK_MODEL` | `--attack-model` | `attack.py` | Nemotron 3 Ultra |
| intent and situation graders | `AIRLOCK_GRADER_MODEL` | `--grader-model` | `attack.py`, `reframe.py agent` | Nemotron 3 Ultra |
| utility judge | `AIRLOCK_UTILITY_MODEL` | `--judge-model` | `utility.py`, `reframe.py agent` | Nemotron 3 Ultra |
| distortion confirmation | `AIRLOCK_DISTORTION_CONFIRM_MODEL` | `--confirm-model` | `utility.py`, `reframe.py agent` | Nemotron 3 Ultra |

The defaults live in `attack.py` (`DEFAULT_ROLE_MODELS`) together with list prices
(`MODEL_PRICES`). Upstream answers (reference, baseline and Airlock answers) are not a scoring
role: they stay on the upstream model the system uses.

**Request adapters.** Models differ in what they accept, so `attack.make_llm` builds each request
through a per-model adapter (`MODEL_ADAPTERS`):

- Nemotron 3 Ultra: strict `json_schema`, `reasoning_effort` as given (`none` by default).
- Nemotron 3 Super (`nvidia/nemotron-3-super-120b-a12b`): rejects every `reasoning_effort` value
  and ignores `json_schema` (it answers `match=true`), so it runs in `json_object` mode with the
  schema in the prompt and thinking switched with `chat_template_kwargs.enable_thinking`.
- Nemotron 3.5 Lightning and Nemotron 3 Nano 30B: `json_schema` with the same thinking switch
  (without it, Lightning writes its reasoning into `content`).

Replies are read from `content` only (`reasoning_content` is dropped, as are inline `<think>`
blocks and leading blank lines), validated locally against the schema, and retried once in JSON
mode with the errors in the prompt when they do not parse or validate.

**Calibration.** `calibrate_judges.py` re-runs each role with cheaper candidates on a stratified
sample of stored (system, case) items: the harness and proxy never run, and the stored Ultra
outputs are the reference, so Ultra is not paid twice. Roles are isolated (a candidate grader
grades Ultra's stored attacks, a candidate judge sees the exact answer pair and order Ultra saw,
a candidate confirmation re-checks exactly Ultra's flags), and Ultra re-runs the cheap roles to
show its own noise. It reports Cohen's kappa, Spearman and mean absolute difference, the change
in every headline rate per system and pooled, ranking reversals, and tokens and dollars per role
and model. Calls are cached in `results/judge-calibration/calls.jsonl` and capped by
`--max-tokens` (2M by default); the estimate prints first and the sample shrinks to fit.

```bash
uv run eval/calibrate_judges.py --dry-run      # sample and estimate
uv run eval/calibrate_judges.py --yes          # run
uv run eval/calibrate_judges.py --report-only  # rebuild results/JUDGE_CALIBRATION.md from the cache
uv run eval/calibrate_judges.py --roles distortion_confirm --candidates nvidia/Nemotron-3_5-Lightning \
  --retest-roles --per-stratum 3 --sensitive-extra 0 --tag confirm-lightning --yes  # follow-up
```

A candidate takes a role only if every headline rate of the role stays within ±3pp of Ultra
(±0.03 for the utility ratio), pooled and per system, with no ranking reversal. In the study
(`results/JUDGE_CALIBRATION.md`, 1.72M tokens, about $0.51) no candidate met that bar for any
role: Super as attacker inferred more situations (+10pp), Super as utility judge confirmed 15pp
fewer distortions, Lightning as confirmation model moved distortion by -3.5pp on 144 items and by
-8pp for one system, Nano as grader called 22pp more situations inferred. Ultra therefore stays
the default everywhere; the cheaper models remain one flag away for pilots and smoke runs.

## Known limitations

- **Paraphrased leaks are invisible to the scanner.** `attack.py` (below) is the complement that
  catches some of them. Matching is by string and normalization. If Airlock or the
  cloud-bound prompt rewrites `stage II HER2-positive breast cancer at Maplecrest General` as
  `early HER2+ cancer at a hospital in Maplecrest`, nothing is flagged even though a fragment of
  identity survived. A transliteration (`Thornbury` as `손버리`) or a translation is also missed.
- **Partial leaks are not counted.** If 12 of 16 card digits survive, the full number is not present.
  Add fragments as separate `must_not_leak` values when partial exposure matters.
- **Quasi-identifier leakage is approximate.** It counts co-occurring surface forms against a
  hand-set `k`. It does not model population uniqueness (k-anonymity in the statistical sense), and
  it misses attributes that were generalized too little (`61` as `early 60s` is treated as safe).
- **The audit record is self-reported.** The harness trusts Airlock's own log of what it sent. To
  verify independently, point `AIRLOCK_UPSTREAM_BASE_URL` and `AIRLOCK_TAVILY_BASE_URL` at a
  recording proxy and compare its capture with the audit log.
- **Gate save attribution has bounds, not a point value** (see above).
- **Vault state leaks across cases in a run.** Declared terms are global. The dataset isolates vault
  names, and `--reset-vault` clears terms before a run (`DELETE /vault/terms` removes single
  terms), but terms declared by earlier cases in the same run stay active.
- **Synthetic distribution.** Templates cover common patterns in Korean and English but are not a
  sample of real traffic. Rates are comparable across Airlock versions and protection levels, not
  estimates of real-world leak probability.
- **Latency depends on hardware and concurrency.** Report the machine and `--concurrency` with any
  latency number.

## Contract notes

The harness uses only the documented contract, plus the following observations about the current
server:

- `--protection-level` is a server setting, not a per-request parameter. The harness records it,
  sends it as a harmless `x-airlock-protection-level` header, and checks `/healthz`.
- The harness sends `x-airlock-conversation-id` so passes are independent (see the flag table).
- `POST /vault/terms` is called with `{"terms": [...]}` only, so the server's default type is used.
  `POST /vault/reset` is called only with `--reset-vault`.
- A 409 `airlock_review_required` carries `review_id`, `reasons` and `proposed[].span_id`. The
  harness records the held request's audit id; with `--auto-approve-review` it sends
  `POST /review/{review_id}` with `{"approve": [all span_ids], "reject": [], "add": []}` and scores
  the audit record of the request id returned by that call.
- Placeholder syntax (`[[TYPE_N]]` or `<TYPE_N>`) does not matter to the scanner: it only looks for
  planted values and `must_keep` strings. `utility.py` and `attack.py` accept either.
- `timings_ms` keys are not fixed by the contract. Overhead is `total` minus any key matching
  `upstream|tavily|cloud|remote|provider`.
- Gate reasons are matched by hash prefix. Any reason format that embeds the first 12 hex characters
  of `HMAC-SHA256(key, value)` (or of `sha256(value)`) works for the lower-bound attribution.
